# ADR 0002 — Постоянный локальный процесс llama-server вместо llama-cli на каждый запрос

Статус: принято · 2026-10-09 · реализация `arabica/backend.py`

**Контекст.** Каркас v0.2 запускал `llama-cli` на каждый фрагмент: веса (7–11 ГБ) перечитывались каждый раз, формат чата и флаги не совпадали с актуальной сборкой. ТЗ предпочитает встроенный вызов, но допускает отдельный процесс строго на 127.0.0.1.

**Решение.** Один долгоживущий `llama-server`:
- `--host 127.0.0.1`, случайный свободный порт, случайный ключ `--api-key` на сессию (проверено: запрос без ключа отклоняется);
- HTTP через `http.client` напрямую, переменные `*_PROXY` и `LLAMA_ARG_*` вычищаются из окружения дочернего процесса;
- `--jinja` (встроенный шаблон GGUF) + `chat_template_kwargs.enable_thinking=false`;
- потоковая выдача (SSE): отмена и «зависание» (нет токенов N секунд) закрывают соединение, движок остаётся пригоден;
- Windows Job Object `KILL_ON_JOB_CLOSE`: сервер умирает вместе с GUI;
- коды завершения переводятся в понятные сообщения (`0xC000001D` → несовместимый процессор; нехватка памяти; битая модель).

**Альтернатива** — встроенная библиотека (`llama.dll` через ctypes) — отложена: требует собственной обвязки C-API, которая меняется между версиями; выгода (отсутствие loopback-сокета) не перевешивает риск в 1.0. Пересмотреть при аудите Astra.

**Доказательства.** discovery run 37980759249 (реальные модели), `tests/test_engine.py` (fake-сервер: постоянство PID, отмена, авторизация, сбой процесса, битый GGUF, кириллический путь с пробелом).
