# Задание Claude — ведущий разработчик Arabica AI Pro

## Твоя роль и конечный результат

Ты **единственный основной исполнитель программирования** этого проекта: архитектор реализации, разработчик GUI/backend, лингвистический инженер, инженер сборки и тестирования. Astra выполняет отдельный независимый аудит и архитектурный review, ChatGPT координирует и принимает результаты.

**Цель:** настоящий автономный Windows 10 x64 переводчик **русский ↔ литературный арабский (MSA / фусха)**. Нельзя ограничиваться концептом, HTML-демонстрацией, stub-переводом, ноутбуком, ссылкой на модель либо программой, которая скачивает что-то при запуске/установке. В готовый дистрибутив входят реальные веса модели, llama.cpp/движок, GUI, словари, зависимости, лицензии, инструкции и SHA-256.

**Источники требований:** `TECHNICAL_SPEC.md`, `BENCHMARK_PLAN.md`, `RELEASE_ACCEPTANCE.md`; при противоречиях документируй ADR, не меняй рамки самостоятельно.

## A. Лингвистика и проверка моделей

1. Сформируй `LINGUISTIC_CONTRACT.md`: правила режимов «точный», «литературный», «профессиональный», ограничения на пропуски и добавления, грамматику обеих языковых систем, терминологию, имена, даты, отрицания и числа.
2. Сформируй реалистичный, воспроизводимый тестовый набор **не менее 400 кейсов** (200 RU→MSA, 200 MSA→RU) с лицензированными или собственными исходными текстами и эталонами/экспертной разметкой. Не считай автогенерированные референсы независимой экспертизой. Отдельно маркируй кейсы, требующие проверки профессиональным переводчиком.
3. Сравни кандидатов Qwen3.5-9B Q6_K и Qwen3-14B Q5_K_M в реально запускаемом CPU-бэкенде на одинаковом наборе, соблюдая chat templates каждого кандидата. Предложи более эффективный кандидат только с обоснованием и лицензией. Размер/скорость/качество — из замеров, а не ожиданий. Итоговую модель выбирай после сравнительных тестов, согласования с Astra.
4. Создай переводческие шаблоны сообщений для обоих направлений, трёх режимов, карточки слова, терминологического контроля, контекста документа. По умолчанию показывай только перевод, без chain-of-thought.
5. Спроектируй и реализуй локальный глоссарий SQLite: область, допустимые переводы, выбранный эквивалент, запретные/ошибочные варианты, примеры, источники, версии; экспорт/импорт. Не выдавай непроверенные соответствия за словарные нормы.
6. Реализуй сегментацию больших документов с переносом контекста, контроль отрицаний/чисел/имён, мягкую диагностику возможных потерь смысла без фиктивных гарантий, огласовки и русскую транскрипцию **по запросу**.

## B. Реальная программа

7. Создай исполняемый проект в Git-репозитории: PySide6 (Qt) GUI, Python-сервисы, локальный llama.cpp runtime, SQLite; надёжный адаптер к модели. Разреши только локальную обработку: без интернет API, телеметрии, самозагрузки и фоновых обновлений. Не требуй устанавливать Python вручную на конечном ПК.
8. GUI на русском: поле исходного текста, переключение направления, режимы, результаты/копирование, история, карточки слов, глоссарий, настройки, импорт/экспорт TXT и DOCX, стабильное RTL/LTR выделение и раскладка. Не блокируй UI во время инференса, реализуй отмену и статусы.
9. Учитывай неизвестные CPU/GPU: CPU-only базовый путь; проверь runtime-потребление ОЗУ, флаги CPU/AVX2, чистый Windows 10, предупреждения о несовместимости. GPU ускорение — необязательная опция, не единственный путь работы.
10. Unit, integration, linguistic regression и реальный model smoke. Проверить оба направления перевода, Unicode RTL, кириллические пути, большой текст, отмену, отсутствие модели/битую модель, ошибку при недостатке памяти, историю, экспорт, перезапуск, удаление. Добавить удобный `--self-test` без сетевых обращений.

## C. Выпуск с уже вложенной моделью

11. Сборка на **Windows x64** (например, Windows GitHub Actions runner с подходящим доступным диском или Windows-сборочная машина). Заранее зафиксируй версии, источники и SHA-256 исходных GGUF. Следи за фактическими ограничениями диска/памяти CI. Никаких обещаний, что любой бесплатный runner вместит сборку 10+ ГБ.
12. Упакуй приложение со всеми бинарными зависимостями через PyInstaller onedir или строго мотивированный эквивалент, затем Inno Setup многофайловым установщиком (ориентир DiskSliceSize=1800000000). Полученные `setup.exe` и `setup-*.bin` должны лежать рядом, каждый файл менее 2 GiB.
13. Создай `SHA256SUMS.txt`, `manifest.json`, `INSTALL_OFFLINE_RU.txt`, `LICENSES/`, `KNOWN_LIMITATIONS.md`, `TEST_REPORT.md`, `BENCHMARK_RESULTS.md`, `RELEASE_NOTES.md`. Не нарушай лицензионные ограничения исходной модели, GGUF, Qt/PySide6 и тестовых данных.
14. До маркировки релиза выполни **реальный offline smoke на Windows 10**, сеть физически отключена, пользователь без дополнительного Python/VC/моделей, файл модели уже на диске в пакете. Установи со скопированных с телефона/USB частей. Выполни реальный RU→MSA и MSA→RU перевод, экспорт, перезапуск. Запиши доказательства: версия ОС, загрузка модели, файлы, логи, время, peak RAM, результат.
15. Только после прохождения гейтов опубликуй **полный** GitHub Release с частями установщика (каждая менее 2 GiB), контрольными суммами и инструкцией. Если не можешь запустить сборку или тест на Windows, верни честный статус BLOCKED с точной командой и необходимыми ресурсами; не называй ZIP с исходниками готовым релизом.

## D. Взаимодействие с Astra

- Перед реализацией зафиксируй с Astra решение по моделям, backend и лицензиям в `ADR/`.
- Дай Astra доступ к проверяемому исходному коду, списку зависимостей, pipeline, test reports, hashes; исправляй блокирующие замечания с коммитом и ссылкой на тест.
- При ревью сохраняй трассировку `finding → fix → test evidence`. Не заменяй независимую проверку собственным утверждением «всё работает».

## Отчёт по каждому этапу

Сообщай: commit SHA, список изменённых файлов, воспроизводимые команды сборки, результаты тестов, что **реально** проверено, что остаётся blocked, следующий конкретный шаг. Не трать работу на нефункциональные макеты раньше реального двустороннего инференса. Сначала working translation → затем UI → затем полный офлайн-инсталлятор и испытания.
